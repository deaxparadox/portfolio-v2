# Chapter 3
# Application Architecture & Layout Philosophy

---

# 1. Introduction

Portfolio v2 is not built as a traditional website.

It is built as an application.

However,

it must always remain a portfolio.

The application architecture exists to improve exploration,
navigation,
performance,
and interaction.

The visitor should never feel like they need to "learn" the interface.

Instead,

the application should disappear into the background.

---

# 2. Root Layout Philosophy

The application contains two persistent workspaces.

They are siblings.

Never parent/child.

```

```
Application Root

├── Primary Workspace

└── Companion Workspace
```

The portfolio exists inside the Primary Workspace.

Deax exists inside the Companion Workspace.

Neither owns the other.

---

# 3. Why Sibling Containers?

A common implementation would place the assistant inside the page.

Portfolio

└── Assistant

This architecture has several disadvantages.

• assistant lifecycle depends on page lifecycle

• conversation state is harder to preserve

• routing can accidentally recreate assistant state

• assistant becomes "part of a page"

Instead,

Portfolio v2 treats the assistant as another workspace.

Application

├── Workspace

└── Assistant

This allows each workspace to evolve independently.

---

# 4. Primary Workspace

The Primary Workspace contains the portfolio.

Responsibilities

• routing

• navigation

• content

• projects

• experience

• resume

• engineering pages

• search results

Everything the visitor reads lives here.

---

# 5. Companion Workspace

The Companion Workspace contains Deax.

Initially supported modes

• Chat

• Voice

Future possibilities

• Notes

• References

• Session History

• Context Viewer

• Screen Annotation

The architecture should support future expansion without redesigning the layout.

---

# 6. Initial State

Application starts with

Primary Workspace

100%

Companion Workspace

Hidden

Visitors should immediately focus on the portfolio.

The assistant should never compete for attention.

---

# 7. Opening Assistant

When the visitor requests assistance

Primary Workspace

↓

Animated resize

↓

Companion Workspace expands

Conversation begins

The portfolio remains visible.

The assistant never replaces the content.

---

# 8. Closing Assistant

Closing the assistant

does NOT navigate.

does NOT reload.

does NOT affect routing.

Instead

Assistant disconnects.

Voice session ends.

Resources cleaned.

Primary Workspace smoothly expands.

The user returns exactly where they left off.

---

# 9. Persistent State

The assistant owns its own lifecycle.

Portfolio navigation should never reset

• chat history

• assistant context

• voice session state

unless explicitly requested.

This creates a premium application experience similar to professional desktop software.

---

# 10. Context Sharing

The portfolio should publish context.

The assistant listens.

Example

Current Page

Voice Agent

Section

Architecture

Technologies

LiveKit

Redis

FastAPI

Current Scroll Position

Architecture Section

The assistant automatically understands

• what page is active

• which project is active

• what section the visitor is reading

The assistant should never need to ask

"What project are you referring to?"

---

# 11. Loose Coupling

Communication should be event-driven.

The portfolio should never directly manipulate the assistant.

Instead

Portfolio

↓

Publish Context

↓

Assistant

↓

React

Likewise

Assistant

↓

Navigation Request

↓

Router

↓

Navigate

This keeps both systems independent.

---

# 12. Routing Philosophy

Everything important has a URL.

Examples

/

/projects

/projects/staffmind

/projects/voice-agent

/experience

/resume

/contact

The assistant does NOT require routing.

It is part of the application shell.

---

# 13. Layout Persistence

Only content changes.

Never destroy

Header

Navigation

Application Shell

Assistant

Theme

Search

Persistent layouts reduce visual noise.

Visitors always know where they are.

---

# 14. Navigation Philosophy

Navigation should feel instantaneous.

Pages should not appear to disappear.

Instead,

content transforms.

The user should feel like

they are moving through one application,

not opening many pages.

---

# 15. Responsive Philosophy

Desktop

Primary Workspace

+

Companion Workspace

Tablet

Assistant becomes drawer

Mobile

Assistant becomes bottom sheet

Architecture remains identical.

Only presentation changes.

---

# 16. Assistant Philosophy

Deax is not a chatbot.

Deax is a companion.

Purpose

Explain

Guide

Teach

Navigate

Never distract.

Never advertise itself.

The portfolio remains the primary product.

---

# 17. Loading Philosophy

Skeleton loading is mandatory.

Even static pages should display skeletons.

Reasons

• smoother perceived performance

• prevents layout shifts

• creates consistency

• improves transitions

Skeletons should resemble final content.

Never generic grey blocks.

---

# 18. Rendering Philosophy

Content should be generated statically whenever possible.

Interactive islands hydrate only when necessary.

Examples

Hydrate

• LiveKit

• Chat

• Mermaid

• Search

• Image Gallery

• Motion Components

Everything else should remain static.

The visitor should never think

"This is a cool application."
